# 커뮤니티 지도 추천

홈 화면 상단 `OO님을 위한 추천 지도` 캐러셀에 들어갈 커뮤니티 지도를 골라주는 기능이다.

---

## 1. 무엇을 하는 기능인가

로그인한 사용자에게 **관심사가 비슷한 커뮤니티 지도**를 5개 추천한다.

"관심사"는 따로 입력받지 않는다. **사용자가 이미 참여 중인 지도의 태그**를 보고 추론한다.
`#맛집 #카페` 지도에 참여 중인 사람에게는 비슷한 태그를 가진 다른 지도를 보여주는 식이다.

참여한 지도가 하나도 없는 신규 가입자에게는 **인기 있고 최근에 만들어진 지도**를 대신 보여준다.
어떤 경우에도 빈 목록을 주지 않는다. 홈 화면이 비어 보이면 기능이 없는 것처럼 보이기 때문이다.

---

## 2. API

```
GET /api/v1/maps/recommendations?size=5
Header: X-User-Id   (선택 — 게이트웨이가 넣어준다. 없으면 인기순으로 응답)
```

`size`를 생략하면 5개, 최대 20개까지 요청할 수 있다.

```json
{
  "success": true,
  "data": [
    {
      "id": 12,
      "name": "서울 팝업스토어 맵",
      "description": "요즘 뜨는 팝업 모음",
      "imageUrl": "https://...",
      "type": "COMMUNITY",
      "tags": ["팝업", "데이트코스"],
      "memberCount": 2300,
      "reason": "관심 태그 #데이트코스와 비슷해요"
    }
  ]
}
```

`reason`은 **왜 이 지도가 추천됐는지**를 사용자에게 보여주는 문구다.
추천이 이상할 때 원인을 찾는 단서로도 쓰인다.

> 게이트웨이 라우팅은 `/api/v1/maps/**`로 이미 잡혀 있고 GET은 인증 없이 통과하므로,
> 이 기능 때문에 게이트웨이 설정을 바꿀 필요는 없다.

---

## 3. 추천이 정해지는 과정

```
1) 관심 프로필 만들기   내가 참여한 지도들의 태그를 모아 가중치를 매긴다
2) 후보 모으기         태그가 겹치는 커뮤니티 지도 + 인기 지도
3) 점수 매기기         태그 유사도 · 인기도 · 신선도를 합산
4) 다양성 보정         비슷한 지도만 나오지 않도록 조정
5) 상위 N개 응답        추천 이유를 붙여서 반환
```

### 1) 관심 프로필

태그를 단순히 모으기만 하면 세 지도에 모두 있는 `#맛집`과 한 지도에만 있는 `#캠핑`이 같은 무게가 된다.
그래서 태그마다 가중치를 매긴다.

```
태그 가중치 = 등장 횟수 × 역할 가중 × 최근성 가중

역할 가중  : 내가 만들거나 운영하는 지도(OWNER·ADMIN) 1.5 / 그냥 참여 1.0
          / 초대로 들어간 프라이빗 지도의 일반 멤버 0.4
최근성 가중: 참여한 지 오래될수록 작아짐 (60일 기준 지수 감쇠)
```

프라이빗 지도에 초대받아 그냥 멤버로만 있는 경우는 가중을 0.4로 낮춘다.
**초대로 들어간 지도는 내가 고른 컨셉이 아니기 때문**이다 — 친구가 만든 모임 지도에 참여했다고 해서
그 지도의 태그가 내 취향이라고 보기는 어렵다.

**커뮤니티 지도와 프라이빗 지도를 모두 재료로 쓴다.** 비공개 지도에서도 취향이 드러나기 때문이다.
다만 **추천 결과로는 커뮤니티 지도만 나가므로** 비공개 정보가 노출되지 않는다.
`reason`에도 지도 이름 대신 태그만 쓴다. 화면을 옆에서 보는 사람에게 비공개 지도 이름이 새면 안 되기 때문이다.

### 2) 후보 모으기

전체 지도를 다 채점하면 지도가 늘어날수록 느려진다. 그래서 두 단계로 나눈다.

- **태그가 겹치는 지도**를 겹친 개수가 많은 순으로 먼저 채운다
- **인기 지도**로 남은 자리만큼만 채운다 (다양성 확보 + 관심 프로필이 비었을 때의 유일한 후보)
- 여기서 **이미 참여한 지도와 내가 만든 지도는 제외**한다

후보는 최대 300개로 제한한다. 지도가 몇 만 개가 돼도 점수 계산은 항상 300개만 한다.

### 3) 점수 매기기

```
점수 = 태그 유사도 × 0.55 + 인기도 × 0.25 + 신선도 × 0.20
```

| 요소 | 계산 방식 | 왜 이렇게 했나 |
|---|---|---|
| 태그 유사도 | 관심 벡터와 지도 태그의 **코사인 유사도** | 겹친 개수만 세면 "내가 중요하게 여기는 태그"가 반영되지 않는다 |
| 인기도 | `log(멤버 수)` 를 0~1로 정규화 | 원본 값을 쓰면 멤버 수천 명인 지도가 다른 요소를 압도해 개인화가 무의미해진다 |
| 신선도 | 생성일 기준 지수 감쇠 (90일) | 오래된 지도만 계속 노출되는 것을 막는다 |

**참여 이력이 없으면** 태그 유사도가 항상 0이라 모든 후보가 같은 점수가 된다.
이때는 위 가중치 대신 **콜드스타트 전용 가중치**(인기도 0.80 / 신선도 0.20)를 쓴다.
처음엔 태그 몫 0.55를 인기도·신선도에 비례 배분하는 방식이었지만, 그 배분 비율은 아무도 결정한 적 없는
파생값이었고 실제로 적용해보니 신선도 비중이 2.2배로 뛰어 멤버가 가장 많은 지도가 순위에서 밀려나
"지금 많이 찾는 지도예요"라는 의도와 어긋났다. 그래서 별도 설정값으로 분리했다.

### 4) 다양성 보정

점수 상위 5개를 그냥 자르면 **전부 `#맛집` 지도**가 되기 쉽다. 실제로 그렇게 된다.

그래서 하나씩 뽑을 때마다 이미 고른 지도와 비교해서 감점한다.

- 태그가 많이 겹칠수록 감점 (`tag-overlap-penalty`)
- 같은 사람이 만든 지도는 1개까지만 (`max-per-owner`)

## 4. 설정

가중치가 코드에 박혀 있으면 조정할 때마다 배포해야 한다. 그래서 `application.yml`로 뺐다.

```yaml
map:
  recommendation:
    default-size: 5          # size 파라미터 없을 때 개수
    max-size: 20             # 한 번에 요청 가능한 최대 개수
    candidate-limit: 300     # 점수를 매길 후보 상한
    weights:
      tag: 0.55              # 합이 1이 되도록 유지
      popularity: 0.25
      freshness: 0.20
      cold-start:            # 참여 이력이 없을 때(콜드스타트) 쓰는 전용 가중치. tag는 항상 0이라 나머지 둘의 합이 1이다.
        popularity: 0.80     # "지금 많이 찾는 지도예요" 문구에 맞게 인기도가 결과를 주도한다
        freshness: 0.20      # 신선도는 오래된 지도를 밀어내는 역할만 한다
    diversity:
      max-per-owner: 1           # 같은 소유자 지도 최대 개수
      tag-overlap-penalty: 0.15  # 태그 겹칠 때 감점 정도
    profile:
      manager-role-weight: 1.5      # OWNER·ADMIN 지도 가중
      invited-member-weight: 0.4    # 초대로 들어간 프라이빗 지도의 일반 멤버 가중 (내가 고른 컨셉이 아님)
      recency-half-life-days: 60    # 참여 시점 감쇠 기준
      freshness-half-life-days: 90  # 지도 생성일 감쇠 기준
```

**추천 결과를 손보고 싶으면 이 값만 바꾸면 된다.**
예를 들어 개인화를 더 세게 하고 싶으면 `tag`를 올리고 `popularity`를 내린다.

## 5. 코드 구조

```
map/recommendation/
├─ MapRecommendationService   전체 흐름을 엮는다 (DB 조회는 여기서만)
├─ UserInterestProfiler       참여 지도 → 관심 태그 가중치
├─ MapScorer                  후보 지도에 점수 매기기
├─ DiversityRanker            다양성 고려해 최종 선별
├─ InterestProfile            관심 태그 벡터 (유사도 계산 포함)
├─ JoinedMap / ScoredMap      계산용 값 객체
├─ RecommendationReason       추천 이유 문구 생성
└─ RecommendationProperties   설정값

map/controller/MapRecommendationController   엔드포인트
map/dto/MapRecommendationResponse            응답 DTO
```

`UserInterestProfiler` · `MapScorer` · `DiversityRanker`는 **DB나 스프링 컨텍스트에 의존하지 않는 순수 계산**이다.
덕분에 단위 테스트가 빠르고, 가중치를 바꿔가며 결과를 실험하기 쉽다.

## 6. 이번에 추가·변경된 것

### 새로 만든 것
- `map/recommendation/` 패키지 전체 (위 구조 참고)
- `MapRecommendationController` — 추천 엔드포인트
- `MapRecommendationResponse` — 응답 DTO
- 추천 테스트 45개 (단위 34 + 리포지토리 5 + API 6). map-service 전체는 21 → 73개
  (73에는 추천과 별개인 태그 정규화 테스트 7개가 포함돼 있다)

### 기존 파일 중 손댄 것
| 파일 | 변경 내용 |
|---|---|
| `MapEntityRepository` | 후보 조회 쿼리 3개 추가 |
| `MapMemberRepository` | `findByUserId` 추가 |
| `MapServiceApplication` | `RecommendationProperties` 등록 |
| `application.yml` | `map.recommendation` 설정 블록 추가 |

**기존 API·응답 형식은 하나도 바뀌지 않았다.** 전부 추가만 했다.

## 7. 알아두면 좋은 것

### 실시간 계산이다 (배치·스케줄러 없음)
요청이 올 때마다 계산한다. 쿼리 3번과 후보 수백 건의 산술 연산이라 가볍다.

배치로 미리 계산해두는 방식도 검토했지만 택하지 않았다.
- 갱신 주기만큼 결과가 낡는다. **지도에 참여했는데 추천에 그 지도가 계속 떠 있게 된다**
- 신규 가입자는 다음 배치가 돌 때까지 추천을 못 받는다
- 추천 결과 테이블·배치 잡·미계산 사용자 폴백까지 만들어야 해서 오히려 코드가 늘어난다

### 캐시도 아직 없다
map-service에는 Redis 의존성이 없고, 현재 계산량에서는 캐시가 이르다.
필요해지면 Redis를 새로 붙이기보다 `spring-boot-starter-cache` + Caffeine(인메모리)이 간단하다.

### LLM(Gemini)은 쓰지 않는다
요청 경로에 넣으면 응답이 수 초로 늘고 비용이 사용자 수에 비례해 커진다.
쓴다면 **태그 동의어 정리**(`맛집` / `맛집투어` / `먹방` 을 같은 개념으로 묶기) 같은
오프라인 배치 용도가 적합하다. 이건 다음 과제로 남겨뒀다.

### 비용
새로 붙인 인프라나 외부 API 호출이 없다. **추가 과금이 발생하지 않는다.**

## 9. 직접 확인해보기

```bash
# 지도 만들기 (태그를 다르게 해서 몇 개)
curl -X POST http://localhost:8083/api/v1/maps \
  -H 'X-User-Id: 1' -H 'Content-Type: application/json' \
  -d '{"name":"내 맛집 지도","visibility":"PUBLIC","tags":["맛집","카페"]}'

# 추천 받기
curl 'http://localhost:8083/api/v1/maps/recommendations?size=5' -H 'X-User-Id: 1'

# 로그인 안 한 상태 (인기순으로 나온다)
curl 'http://localhost:8083/api/v1/maps/recommendations'
```

게이트웨이를 거칠 때는 `X-User-Id`를 직접 넣지 않고 `Authorization: Bearer <토큰>`을 쓴다.
게이트웨이가 토큰을 검증해 `X-User-Id`로 바꿔 넣어준다.
